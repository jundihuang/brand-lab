# BrandLab v0.3.1 — M3.1 Validation Hardening Plan

- Date: 2026-10-15
- Scope: schema and validation hardening only.
- Goal: invalid persisted state fails early, errors identify the file and field, and supported writes do not leave ambiguous partial state.

## Tasks

| # | Task | Approach |
|---|---|---|
| 1 | Complete core schemas | Keep existing schemas; add approval state, content audit, discovery manifest, history event, market onboarding, and translation writeback result contracts. |
| 2 | Validate persisted business state at boundaries | Validate data through central read/write helpers for brand, catalog, guideline, glossary, job, plan, approval, audit, result, report, and history. |
| 3 | Standardize schema errors | Emit a stable `SCHEMA_INVALID` code, file path, JSON path, field name, reason, and repair hint. |
| 4 | Standardize safe paths | Reject workspace/job paths that escape their root. |
| 5 | Avoid partial writes | Use atomic replacement for generated text/JSON/JSONL and stage multi-file job updates before replacing current files. |
| 6 | Improve recovery guidance | Document schema, JSONL, digest, approval, and plan failures with concrete repair steps. |

## Validation boundaries

1. `brand.yaml` is validated after market defaults are applied.
2. Every catalog row is validated on read and write.
3. Every active guideline is validated while loading.
4. Every glossary row is validated while loading.
5. Job manifests are validated on load and before save.
6. Translation inputs and normalized translations are validated before state changes.
7. Audit results, existing translation audits, approvals, execution results, and onboarding reports are validated before publication.
8. Plans are validated on every load and save.
9. History events are validated before append.

## Raw data boundary

Shopify raw API responses and connector command logs remain diagnostic artifacts. They are immutable evidence, not normalized business state. Schemas apply to normalized discovery records, plans, results, reports, and workspace state.

## Exit criteria

1. Corrupt or semantically invalid files fail with a stable error code and file/field detail.
2. Core read/write paths cannot persist schema-invalid business objects.
3. New tests prove invalid input is rejected before state mutation.
4. Full test suite passes.
5. Documentation records the validation architecture and recovery steps.
